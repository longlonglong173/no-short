# NS-19 — Local usage anomaly and month scenario

Design fixed before implementation, 2026-10-27. Authorized implementation under the locked NS-19 brief; no additional design approval gate.

- Two separate controls, anomaly and month scenario, default off. Native advanced Budget settings persist them, selected provider, and a third explicit macOS anomaly notification opt-in (also off). Refresh never requests permission. React History persists only its local opt-ins; no OS notifications.
- Pure Swift and TypeScript projections reuse one snapshot's history, provider and timezone. No extra usage reports, network or model calls, schema change, billing claim, productivity inference, or export scope change.
- Baseline: the last 7 observed daily aggregates strictly before today, within the previous 30 calendar days inclusive; ALL 7 must be fully priced. Never skip a recent unpriced observation to backfill an older priced one. Selected-provider rows are combined by calendar date. Missing dates are not inserted as zero. Unpriced observed dates are counted and disclosed. Fewer than 7 observations means insufficient history; any unpriced selected observation blocks both conclusions. Any model marked fallback/unpriced/mixed is insufficient pricing for a complete-cost claim, even if a malformed legacy producer labels the parent estimated; absent provenance preserves legacy estimated semantics and is disclosed as unavailable.
- Anomaly: a complete observed current-day estimate strictly greater than 2 × the sample median, and median > 0. Zero median is insufficient baseline, never an infinite percentage. Show sample count/range, median, multiplier and threshold. An absent current-day row suppresses both outputs as insufficient current data, never measured zero.
- Month output is a **scenario**, never a billing prediction: recorded month estimate + arithmetic mean of the 7 sample days × calendar days remaining AFTER today. State that future daily usage is assumed to resemble these observed retained-log days. Any unpriced observed current-month day prevents a scenario; no exact total is made from a known subtotal. First/last day and leap months use the snapshot timezone's Gregorian calendar.
- Suppress numerical conclusions for errors, stale flag, age >45s, future timestamp >60s, or changed local calendar day, matching NS-17/native freshness. Preserve independent reader errors in the UI. Recompute from each consistent snapshot after provider/source/timezone/pricing changes; never retain calculated values across snapshots.
- Price basis/revision and per-model origins/rates come from the snapshot and are visible beside results. No claim of account-wide coverage; retained days and unpriced dates are explicit. Arithmetic overflow is insufficient data.
- Notification dedup is separate from budget/context tracking: SHA256(source, timezone, provider, local day), persisted before attempted send, at most one attempt per key across refresh/restart/rule edits. Permission denied leaves the in-app result working and displays a notice. Source/provider/timezone/day changes create distinct keys. No session names or prompts enter a notification.
- Chosen approach: small pure projection modules with a shared synthetic JSON fixture and thin native/React views, reusing the existing settings window and notification service. This avoids adding a second scanner or financial forecasting engine. Both surfaces explicitly label TODAY/CURRENT MONTH and snapshot timezone, independent of the selected History range. Native History receives persisted settings; the popover receives enabled summaries. Exports continue to contain selected retained history only, excluding scenarios.

Implementation plan: failing shared-fixture math/boundary tests; pure projection parity; notification/settings regression tests; native and React integration/localization; browser checks on isolated port 5196; final related suites and documentation. Controller owns independent review and remote work.

## Independent review fix — combined arithmetic overflow

Review found that two individually finite provider rows (`1e308` each) could overflow their combined day and produce a positive anomaly with `$Infinity` in React. The core regression reproduced `anomaly: true` before the fix, and the new browser regression reproduced the positive alert. The TypeScript projection now checks finite numbers in every combined day/range/model aggregate before exposing amounts; raw provider-row price-origin checks remain separate, so legitimate differing provider prices continue to work. The sample mean, anomaly threshold, future multiplication and scenario addition are also checked before their results are exposed. Native code already validates combined aggregates and is unchanged.

Focused final verification: **60 core tests passed** across insights/history/comparison (254 assertions); **7 browser tests passed** across insights/comparison on isolated port 5196; typecheck and `git diff --check` passed. Added cases cover current-day/sample-day/month overflow, legitimate differing provider origins, and future multiplication/scenario-addition overflow while preserving independently valid finite anomaly readings. Browser checks the insights panel contains no Infinity or positive anomaly status for combined-day overflow. RED/GREEN logs: `/tmp/no-short-20261027-wave1/ns19-overflow-{core,browser}-{red,green}.log`; typecheck: `ns19-overflow-typecheck.log`. No unrelated native/full-suite reruns or changes; baseline evidence above remains scoped to the original implementation commit.
