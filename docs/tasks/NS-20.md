# NS-20 — Correct multi-source Codex usage totals

Status: implemented in source; independent PR review/merge and a future versioned runtime release are required. No existing release or installed app is replaced.

## Problem and evidence

Pinned ccusage 20.0.34 can report two separate 110-token sessions as 110 daily tokens when their timestamps, models and counters match. Session rows still show 110 each. The existing NS-08 characterization recorded this behavior.

The immutable upstream source is [`d7555844929ad76ec97a113d1d51c31de92bee35`](https://github.com/ccusage/ccusage/tree/d7555844929ad76ec97a113d1d51c31de92bee35). Its Codex `aggregate.rs` includes the session identity in the usage deduplication key only for session reports. The bounded loader's key also omits the session. This collapses unrelated simultaneous usage in daily reports.

## Identity and compatibility

The vendored patch fixes both sites. A normal usage event is deduplicated by logical session identity, timestamp, resolved model and usage counters. Timestamp/counters alone never identify an event across sessions.

- A validated UUID suffix in a Codex rollout name is normalized to lowercase for deduplication only. This recognizes copies moved to another subdirectory or renamed while retaining the UUID. Presentation/report IDs remain unchanged.
- If a rollout name has no valid UUID suffix, the existing upstream relative rollout identity remains the fallback. The patch does not infer identity from message content or token values.
- Copied events within the same identity count once across roots, including when one copy has a shorter prefix and the other has appended usage. Distinct identities remain independent.
- Explicit fork replay and compaction response-ID handling remain unchanged. A copied compaction response ID remains globally deduplicated.
- Unmarked copies with rewritten UUIDs, or arbitrarily renamed non-UUID files, cannot be distinguished safely from separate sessions and are counted independently. Merely matching counters in different sessions is no longer proof of copied history. The patch does not add a new metadata parser; `session_meta` identity still serves existing replay planning, while normal deduplication uses the validated filename UUID/fallback above.

Public snapshot schema stays v1 and the upstream dependency identity stays 20.0.34. `ns20-session-scope-v1` identifies the local patch. The usage cache namespace includes that revision, so a fresh but undercounted old snapshot is not reused or deleted. The pricing source, API-equivalent cost meaning, localization and provider selection remain unchanged.

## Reproducible build and provenance

[`ccusage-source-lock.json`](../../packages/usage/ccusage-source-lock.json) pins the upstream revision/archive SHA-256, compile-time LiteLLM snapshot revision/SHA-256, patch SHA-256 and Rust 1.98.1. The upstream source's pinned pricing revision is retained. [`ccusage-20.0.34-ns20.patch`](../../packages/usage/patches/ccusage-20.0.34-ns20.patch) is the reviewable source delta; no opaque binary is committed.

The runtime build now verifies the assets and patch, extracts a fresh source tree, dry-runs and applies the exact patch with zero fuzz and no reversal, and uses `cargo build --locked --release` for both macOS targets. Integrity, context, compiler or build errors are fatal. There is no fallback to the unpatched npm executable. Existing license notices are retained and the bundled notices identify the modified upstream source.

Prerequisites on a macOS build host:

```sh
rustup toolchain install 1.98.1 --profile minimal
rustup target add --toolchain 1.98.1 aarch64-apple-darwin x86_64-apple-darwin
RUSTUP_TOOLCHAIN=1.98.1 npm run build:usage
```

Both existing macOS CI build jobs install that toolchain/target pair and require the built reader before native regression tests. The Linux job runs offline integrity/patch tests without requiring a native reader or Rust compilation.

Generated runtime manifests contain `ccusagePatchRevision`, `ccusageSourceRevision` and the actual new binary/archive hashes. The checked-in 0.6.1 release manifest/URLs are preserved because those published archives are immutable and unpatched. A future release must rebuild the runtime with a new release version and publish the matching generated manifest; merging this source PR alone does not patch an existing downloaded 0.6.1 executable. The old npm lock remains the baseline version/platform matrix, not the source of executable bytes for new builds.

## Validation

All logs below are local task artifacts, not deployed or installed-app acceptance:

- Real CLI RED: expected 220 daily tokens, received 110; both session rows were 110. The patched build returns 220 daily/history/provider/model tokens and matching range exports/cost sums.
- Moved-copy RED: the path-only fix returned three session rows for a logical two-session fixture. UUID identity correction returns two rows and 220 tokens, including reversed roots and an uppercase UUID copy.
- Real native regression coverage includes root ordering, stale copied prefixes, append, source removal/re-addition, bounded reports, explicit fork replay, compaction response IDs, CSV/JSON and old cache isolation.
- Offline build-policy tests verify changed asset bytes, patch tampering, exact-context application and refusal to reverse/reapply a patch.
- Both arm64 and x86_64 runtime/helper builds passed local signature checks. ARM compiled MCP smoke uses isolated synthetic logs and a system-only PATH. x86_64 is cross-build evidence, not Intel device execution.
- No real logs, installed app, provider settings, OS permissions or signing keys were modified. Notarization, clean-machine installation and other [NS-05 gates](../releases/0.6.1.md#verification-and-remaining-acceptance) remain separate.
